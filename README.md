# GNSS 定位欺骗检测模块

面向**冷链运输车**与**巡检无人机**的定位欺骗检测。判断当前上报的位置是否可信，
并在被拉偏时给出「偏离多少米可以被发现」的量化结论。

**这不是一个「跑一遍滤波器」的项目。** 它的全部难点在于：如何在
「隧道/高楼峡谷/地库里定位本来就会漂」与「有人正在慢慢把你引偏」之间画线，
并且这条线要有物理与统计上的依据，而不是拍脑袋的米数。

---

## 一句话结论

> **匀速拉偏 0.25 m/s（15 m/min）以上，在把位置拉偏 35–120 米时一定能被发现；
> 干净数据上 24 小时零误报（0 次 CONFIRMED）。**
> 更慢的拉偏（< 0.2 m/s）在物理上无法与惯导自身的漂移区分——原因见
> [第 6 节：不可能性论证](#6-为什么更慢的拉偏抓不到不可能性论证)。

具体的分速率数字见 [`docs/RESULTS.md`](docs/RESULTS.md)（由 `./gradlew evalReport` 实测生成）。

## 1. 威胁模型：攻击者能做什么

我们把攻击者按能力分成几档，检测模块必须对最强的那一档也成立：

| 攻击型态 | 描述 | 接收机自检能否发现 |
|---|---|---|
| **纯压制 (jamming)** | 发射噪声，使 GNSS 失效 | 能（直接失锁） |
| **只偏位置** | 伪造位置，但 Doppler/速度仍是真实的 | 能（残差升高） |
| **一致欺骗 (consistent)** | 接管全部卫星，位置/速度/航向自洽地对应一条假轨迹 | **不能** |
| **缓慢拉偏 (drift)** | 从真实位置出发，以 0.1–2 m/s 的速率慢慢引偏 | **不能** |
| **冻结 (meaconing)** | 中继过去的信号，接收机以为自己在原地没动 | 不能 |
| **重放 (replay)** | 重放 N 秒前的真实位置/速度 | 不能 |
| **幽灵航线** | 车真实停在别处，GNSS 却报告它正沿计划航线正常行驶 | 不能 |

**关键判断：只靠接收机自己，一致欺骗与缓慢拉偏是看不出来的。**
接收机看到的是一片完全自洽的假星座、假位置、假速度——它没有任何理由怀疑。
所以本模块的所有力气，都花在引入**接收机之外的参照**上。

## 2. 核心思路：用「接收机骗不了的东西」去核对它

```
传感器 ─┬─> 环境分类 ───────────────────────> 噪声模型 (σ 随环境变)
        │
        ├─> 惯导估值器 (IMU + 轮速/光流 + 磁罗盘 + 气压)
        │        │  ★ 绝不喂入 GNSS —— 它代表"车自己认为自己在哪"
        │        └──> 独立航位推算 + 诚实的协方差
        │
        ├─> 独立测距 (蜂窝 TA / C2 链路 TWR)  ← 与 GNSS 物理独立的第二把尺子
        ├─> 地图 (路网 / 任务走廊)            ← 射频改不了
        └─> 接收机射频指纹 (AGC / C-N0 / 星座换血)
                    │
                    ▼
         各路独立检验 ──> 归一化统计量 ──> CUSUM + 卡方 ──> 证据融合 ──> 判决
```

### 2.1 三条设计红线

**红线一：GNSS 永不进入估值器。**
常见的做法是把 GNSS 当观测喂进 EKF。但那意味着滤波器会老老实实跟着被欺骗的
位置走——滤波器越"好"，它就越顺从攻击者。这里刻意反过来：估值器只用
**攻击者无法通过射频篡改**的输入（轮速、IMU、磁罗盘、气压计、独立测距），
代表"车自己独立认为自己在哪"，GNSS 则是被检验的对象。

**红线二：阈值从虚警率反解，不从"米数"拍。**
每一个门槛都能回答"为什么是这个数"：
- 单点检验：马氏距离平方，无攻击时服从 χ²(2)。取 α=1e-4 ⇒ 门槛 **18.42**。
- 序列检验（CUSUM）：参考值 k 按最优取 delta*/2；门槛 h 由目标 ARL0
  （平均多少采样才误报一次）反解。我们要求单通道 1 小时误报 ≤ 1 次。
- 独立参照（测距）：误差模型干净（无相关多径），门槛回到纯 4σ 卡方。

**红线三：不知道自己在哪时，必须说"不知道"。**
隧道/地库里 GNSS 不可用 → 输出 **DEGRADED**，而不是 TRUSTED。
冷启动头几十秒没有绝对锚点 → 同样输出 DEGRADED。
这两者的业务后果完全不同：前者是"这段时间的轨迹不能用来结算工时"，
后者是"这条轨迹是可信的"。把它们混为一谈，是这类系统最常见的失职。

## 3. 三个状态

| 状态 | 何时 | 能做什么 | 输出 |
|---|---|---|---|
| **BOOTSTRAP** | 刚上电 / 刚出地库 / 长时间失锁后 | 只做"不需要绝对位置"的检验：射频指纹、接收机自检、运动学、地图 | DEGRADED（若连续异常则 SUSPECT） |
| **TRACKING** | 已建立可信锚点 | 全部检验生效 | TRUSTED / SUSPECT / CONFIRMED |
| **LOST** | GNSS 失锁（隧道/地库/被压制） | 只靠惯导航位，**不产生任何位置类证据** | DEGRADED |

### 3.1 冷启动防骗

开机的那一刻是最脆弱的：还没有任何可靠参照，攻击者从这一刻开始拉偏，
你甚至没有基准去比较。

本模块的处置：
1. **不**拿第一个 GNSS 位置当先验（否则攻击者只需控制第一帧）。
2. 必须连续 50 帧（5 秒）在所有"不依赖位置"的检验上都干净，才建立第一个锚点。
3. 如果 bootstrap 期间连续被判为异常 → **直接报 SUSPECT**，而不是无限期卡在
   "启动中"。（开发中实测过这个死锁：分数累积到 3400+，判决却始终是 BOOTSTRAP。）

## 4. 各路检验与它们的门槛

| 检验 | 参照 | 抓什么 | 门槛依据 |
|---|---|---|---|
| `POS_VS_INS` | 惯导位置 | 位置被拉偏 | χ²(2) @ α=1e-4 + 环境相关的多径预算 |
| `VEL_VS_INS` | 惯导/光流速度模长 | 速度被伪造 | z 检验 + CUSUM；低速段放宽 |
| `SPEED_VS_WHEEL` | 轮速 | 冻结/重放/幽灵航线 | 单边 z + CUSUM |
| `COURSE_VS_HEADING` | 磁罗盘/陀螺航向 | 航向被伪造 | z 检验；机动时关闭 |
| `RANGE_VS_INS` | 蜂窝 TA / C2 TWR | **慢速拉偏**（主力） | 4σ + CUSUM 累积 |
| `MAP_VS_INS` | 路网 / 任务走廊 | 位置偏离可行驶区域 | 路宽 + 2.5σ |
| `ALT_VS_BARO` | 气压计高度 | **只拉高度**（无人机常见） | 绝对差 + 慢速偏置估计（偏置更新速率刻意放慢） |
| `RF_ANOMALY` | 射频层本身 | 星座换血 / C-N0 异常整齐 | 经验阈值 + CUSUM |
| `RX_SELFCHECK` | 接收机自检 | 残差/钟差跳变 | 环境自适应基线 |
| `MOTION_PLAUSIBILITY` | 物理常识 | 超速 / 位置跳变 / 轮速说停却在跑 | 硬上限 |

### 4.1 为什么门槛必须按环境变——以及一个真实的坑

城市峡谷的 GNSS 误差**不是白噪声**，而是相关时间 30–60 秒的慢变过程
（多径造成）。对这样的过程做"每采样"检验，有效独立样本数只有 T/τ 左右。

这带来一个非常隐蔽的实现陷阱，我们踩过并修好了：

> **CUSUM 必须按「有效独立采样间隔 τ」推进，而不是每帧推进。**
> 门槛 h 是按"每 ARL0 个**独立样本**"反解的。若在 10 Hz 数据上每帧推进，
> 独立样本数会被高估 (τ/dt) 倍，ARL0 随之缩短同样的倍数——郊区 τ=5 s 时
> 就等于**每小时误报约 50 次**。开发中实际观察到了"干净数据 100% 触发率"。

修正后，CUSUM 只在累积 τ 秒的信息之后推进一次，推进量是窗口内的平均归一化创新。

### 4.2 独立测距：慢速拉偏的唯一抓手

慢速拉偏的每一次单点偏差都只有 1–3 σ，单点门槛永远打不到。**唯一**能抓住它的，
是一个**无偏、独立、可以长期累积**的参照。

蜂窝 TA（卡车）与 C2 链路双向测距（无人机）就是这样的参照：
- 与 GNSS 完全不同的频段、不同的设备、不同的运营商——**射频欺骗碰不到它**
- 精度很粗（σ 30–90 m），但**无偏**
- 单帧看不出 50 m 的拉偏；但 30 秒的 CUSUM 能把 50 m 的持续偏差累积到远超门槛

**这也直接给出了理论上的"检出半径下界"：约 3–4 倍测距精度。**
实测的 35–120 m 与这个量级一致。

> 注意：**只在惯导自由运行时**才把测距残差喂给 CUSUM。若每帧都重锚，
> 惯导位置就退化成"带 GNSS 噪声的 GNSS 位置"，残差变成自相关序列，
> CUSUM 会在干净数据上单调累积到报警。这是又一个真实踩过的坑。

## 5. 判决与证据融合

### 5.1 为什么不加权平均

加权平均会让"14 条证据里 1 条强烈报警"被稀释掉。而在欺骗检测里，
单条强证据（比如独立测距差了 400 m）本来就该直接定案。

采用**证据累积 + 封顶 + 衰减**：
- 每一路报警贡献一份对数似然比，按该路的可信度加权
- 总 LLR 越过 suspect/confirmed 两级门槛才升级
- 证据按 45 秒半衰期衰减，所以"曾经报警"不会永久污染状态

### 5.2 三级判决与滞回

| 判决 | 含义 | 升级条件 | 降级条件 |
|---|---|---|---|
| TRUSTED | 可信 | — | — |
| SUSPECT | 可疑（证据不足以定案） | 总分 ≥ 2.2，持续 1.5 s | 总分 < 1.1 |
| CONFIRMED | 确认被欺骗 | 总分 ≥ 5.5，持续 2.5 s | 需连续 60 s 低分 |
| DEGRADED | 不知道 | GNSS 失锁 / 无锚点 | 立即 |

**CONFIRMED 降级需要 60 秒，是刻意的**：「确认被骗」这个结论不应随便撤回。

## 6. 为什么更慢的拉偏抓不到：不可能性论证

0.1 m/s（6 m/min）的拉偏检出率是 0/6。**这不是实现问题，是物理限制。**

设未经 GNSS 校正的惯导，其位置误差增长率为 ε·v（ε 是等效距离误差率，
来自磁罗盘残余偏置、轮速标度误差等）。一个速率为 r 的拉偏，在时间 T 内
造成的偏移是 r·T。要把它与惯导自身漂移区分开，需要：

```
r·T  >  n · ε·v·T      （n 是信噪比倍数，约 3–4）
⇒  r  >  n·ε·v
```

也就是说，**可检出的最小拉偏速率与车速成正比、与惯导的相对精度成反比**，
而与观测多久**无关**——看得越久，惯导也漂得越远，信噪比不会变好。

在本仿真里（v≈14 m/s，ε≈3.5%），
`r_min ≈ 3.5 × 0.035 × 14 ≈ 1.7 m/s`——这是**纯惯导**的极限。

实测能做到 0.25 m/s，是因为有两个额外的、与 T 无关的绝对参照在起作用：
1. **独立测距**（TA/TWR）：无偏，误差不随时间增长 → 把 ε 从 3.5% 压到 ~1%
2. **地图约束**：位置不能长期落在路网外

**要抓更慢的拉偏，唯一的办法不是改进算法，而是改进硬件/基础设施：**
- 更高的测距精度（UWB 场站、5G RTT）
- 更好的航向源（双天线 GNSS 罗经、视觉里程计）
- 更密的绝对参照（更多锚点覆盖）

这正是本模块「说真话」的地方：它给出的是能力边界，而不是"什么都能抓"的假象。

卡车：缓慢拉偏 / 跳变接管 / 冻结 / 重放 / 幽灵航线 **全部 6/6 检出**。

强制失锁 120–210 s 期间：**98.2% 的帧判为 DEGRADED**，零 CONFIRMED 误报。

## 8. 已知局限（诚实清单）

1. **一致欺骗 + 极慢速率 (r < 0.2 m/s) 不可检**——见第 6 节的物理极限。
2. **无人机没有绝对航向源时**，航向类检验被关闭（代码中 `droneHasHeadingSource`）。
   这是可观测性问题，不是实现缺陷：光流只给出机体系速度，无法确定航向。
3. **锚点覆盖不足时**（例如郊区没有蜂窝 TA），检出半径退化到纯惯导极限。
4. **本模块的噪声参数是在仿真中校准的**。真实工程里必须用实车采集的数据重新标定
   ——尤其是 `insPosSigma` 中的 ε（等效距离误差率），它直接决定能抓多慢的拉偏。
5. **仿真不能替代台架/外场测试**。对抗真实欺骗器的射频指纹、AGC 响应、
   天线阵列效应，需要考虑更多硬件细节。

## 9. 工程结构与接入

```
src/main/kotlin/io/gnsstrust/
├── core/      纯数学: 矩阵、卡方/正态分位数、CUSUM 的 ARL 标定、地理转换
├── model/     数据契约 (SensorFrame / GnssFix / TruthState ...)
├── est/       ESKF 航位推算估值器 (只吃非射频传感器)
├── detect/    环境分类 / 各路检验 / CUSUM / 证据融合 / 判决状态机
├── sim/       仿真: 场景几何、真值轨迹、传感器误差、攻击模型
├── eval/      评估: 蒙特卡洛、检出半径扫描、虚警率统计
└── cli/       命令行入口
```

### 9.1 接入真实车机的三个接口

模块只暴露三个接口，替换仿真很容易：

```kotlin
// 1. 传感器帧 (100 ms 一帧)
detector.update(frame: SensorFrame): SpoofReport

// 2. 锚点台账 (运营商基站 / C2 地面站坐标, 从配置加载)
detector.anchorPositions = ...

// 3. 地图 (路网 / 任务走廊)
detector.attachMap(roads)
detector.attachCorridor(waypoints, halfWidthM)
```

`SpoofReport` 给你的不只是判决，还有一个更有用的东西：
**`posUncertaintyM`（当前位置不确定度）**。
调度系统可以据此决定"这条轨迹能不能用来结算工时"，而不必等到报警。

### 9.2 依赖

**零第三方依赖**（除了测试框架）。纯 Kotlin + JDK 标准库，
可以直接放进 Android 工程，不需要 NDK、EJML 或 Apache Commons。

## 11. 这个项目里踩过并修好的坑（回归测试都覆盖了）

如果只看最终代码，这些错误不会显现。列出来是因为它们在其他实现里同样容易发生：

| 坑 | 现象 | 根因 |
|---|---|---|
| **轮速拧歪航向** | 轮速 9 m/s，滤波器速度变 5 m/s | 观测 (v, ψ) 不可分辨，H 含 ψ 偏导 |
| **非完整约束同理** | 直行时航向缓慢旋转 | 同上 |
| **重锚后位置跳变** | 单帧跳 70 m | 只重置协方差对角线，未清互协方差 |
| **加计零偏跑飞** | 2 秒内位置飞出数百米 | 零偏先验过宽，吸收所有误差后反号 |
| **CUSUM 每帧推进** | 干净数据 100% 误报 | 门槛按独立样本标定，却按帧推进 |
| **CUSUM 单位错** | 高度差 6 m 被当成 6σ 累积 | 传了米数而不是归一化值 |
| **重锚死循环** | 分数 3400 却一直 BOOTSTRAP | bootstrap 依赖地图检验，缓冲被卡死 |
| **GNSS 速度为零的假象** | 地库里速度估计崩掉 | "退化定位解"报速度 0，被当成真速度 |
| **光流当作世界系速度** | 滤波器"白拿"了航向 | 光流是机体系，必须按航向旋转 |
| **机场悬停积分漂移** | 悬停时报 1.4 m/s | 光流白噪声被积分，无零速约束 |
| **只做窗口变化量的高度检验** | 高度被拉偏 100 m 却得分 0 | 恒定速率的拉偏在窗口两端变化量相等 |

关于最后一条：高度检验必须同时做**绝对差**与**变化量**两件事。只做变化量，
一个以恒定速率缓慢抬高的欺骗会让窗口两端的增量几乎相同，残差恒为 0——
开发中实际观察到高度被拉偏 100 m 而得分始终为 0。修法是加一个刻意放慢的
绝对偏置估计器（z 大时几乎不更新），使真实拉偏不被吸收。
